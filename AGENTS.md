# Repository Guidelines

## Project Overview

Bakery delivery platform for small and mid-sized inland Brazilian cities (target: Paulo Afonso, Bahia). It is the practical artifact of an undergraduate thesis (TCC, Information Systems, UniRios) titled "Desenvolvimento e Avaliação de Usabilidade de um Aplicativo Mobile de Delivery para Panificadoras em Cidades Interioranas". The thesis evaluates how usability affects acceptance and intention to use, measured with SUS (System Usability Scale) and TAM (Technology Acceptance Model) questionnaires.

Customers browse bakeries near them, build a cart, place an order and follow its status. Bakeries register themselves, manage their catalog and process incoming orders. The working product name is still undecided (the Figma prototype uses a placeholder logo/name).

Product principles: simple, minimal UI that follows Nielsen's heuristics; very few taps from opening the app to placing an order; low operating cost for bakeries (no marketplace-style commissions). UI copy is in Brazilian Portuguese (pt-BR).

## Stack

- Front-end: React 19 + TypeScript, built with Vite, routed with TanStack Router, linted with Oxlint, managed with Bun. Hosted on Vercel (hosting only).
- Back-end: Supabase only (BaaS). PostgreSQL, Auth, Storage, Row Level Security, edge functions when needed. There is no custom API server.
- Design reference: Figma prototype (auth screens and home screen exist so far; the rest is still being designed).
- Process: Kanban.

## Project Structure

Application code is under `src/`: `pages/` contains client and bakery screens, `components/` contains reusable UI and registration form steps, `routes/` defines TanStack Router routes, `contexts/` holds shared React state, and `utils/` contains services and helpers such as Supabase access. Shared types live in `src/types/`; images and icons are in `src/assets/` and `public/`. `src/routeTree.gen.ts` is generated by the router tooling; avoid editing it by hand.

## Build, Test, and Development

Use Bun (the repository includes `bun.lock`) or npm to install dependencies. Available scripts:

- `bun run dev` — start the Vite development server.
- `bun run build` — type-check with TypeScript, then create a production build in `dist/`.
- `bun run lint` — run Oxlint on the project.
- `bun run preview` — serve the production build locally after building.

There is no test script or test suite configured currently. Run the build and lint commands before submitting changes.

## Coding Style

Follow the existing TypeScript and React patterns. Use `.tsx` for components and pages, and `.ts` for non-visual logic and types. Name React components and page files in PascalCase (for example, `BakeryCard.tsx`); use descriptive camelCase for functions, variables, and utilities. Keep client-facing and bakery-facing code in their corresponding subdirectories. Match nearby formatting and import conventions; Oxlint is the configured linter. Avoid adding dependencies when existing React, TanStack Router, or Supabase utilities cover the need.

Supabase conventions:

- Use one Supabase client singleton, reused everywhere (never create a client per component). Credentials come from `.env` with the `VITE_` prefix.
- Session state comes from `supabase.auth.onAuthStateChange()` (wrapped in the auth context/hook), not from ad-hoc `getSession()` calls.
- Prefer generated Supabase types (`supabase gen types`) over hand-written row types.
- Schema changes go through SQL migrations; keep scripts idempotent where possible.

## Testing

No automated tests are configured. For UI or route changes, manually exercise the affected client or bakery flow using `bun run dev`, and run `bun run build` and `bun run lint`. If adding tests in the future, keep them next to the feature or in a clearly named test directory and provide a runnable package script.

## Users and Auth Model

Two kinds of users, both authenticating through Supabase Auth (email + password; Google OAuth is planned/undecided and the prototype already shows a Google button):

- **Customer**: needs only email, password and name. No saved address. The device's geolocation is used to find nearby bakeries and is sent along with each order.
- **Bakery**: logs in as a normal Auth user (the owner's account). The business data lives in `bakeries`, linked through `bakeries.owner_id -> profiles.id`. This owner-based design was reconsidered (bakery as its own account type) and the decision was to **keep it**.

Credentials live only in `auth.users`. Never add password columns to `profiles` or `bakeries`.

`profiles` (id = `auth.users.id`, full_name, phone, avatar_url, role, timestamps) is created automatically by the `handle_new_user` trigger (SECURITY DEFINER, `search_path = public`) on `auth.users` insert:

- Name comes from `raw_user_meta_data.full_name`, then `name` (Google), then the email local part, then "Usuário".
- `role` comes from `raw_user_meta_data.role`, but only `owner` is honored; anything else, including `admin`, becomes `customer`. `user_metadata` is client-controlled, so never trust it for privilege. Admin must never be assignable from the client.
- Google OAuth signups always land as `customer`; a bakery signing up via Google needs a post-login step to switch to `owner`.
- Profile rows cannot be inserted from the client (RLS only allows own SELECT/UPDATE), which is why the trigger exists. `profiles.id` has no default and is an FK to `auth.users`, so test profiles must be created by creating an Auth user first (Dashboard -> Authentication -> Users), not by inserting rows by hand.

A future admin panel (for the developer only) should use the `service_role` key on a trusted backend or `app_metadata`, never a client-writable role.

Dev notes for Auth: "Enable Email provider" must stay ON (otherwise signups fail with `email_provider_disabled`). "Confirm email" is currently OFF in development. The built-in Supabase SMTP is heavily rate-limited (429 `over_email_send_rate_limit`), so configure a custom SMTP before usability test sessions or production.

## Data Model (PostgreSQL / Supabase)

The database is the source of truth; some originally planned columns were removed after review, so check the live schema before relying on a field. IDs are `uuid` (anything referencing `auth.users` must be uuid). Open question: `bigint` identity for internal tables such as `orders` (readable order numbers).

- `profiles`: see above. Role enum: `customer | owner | admin`.
- `bakeries`: owner_id, name, cnpj (unique), email, phone/whatsapp, description, logo_url, cover_url, address (cep, street, number, complement, neighborhood, city, state, latitude, longitude), opens_at / closes_at, is_open, delivery_radius_km, estimated_delivery_minutes (optional), pix_key, optional delivery_fee and min_order_value (undecided whether they stay), avg_rating and rating_count (maintained by trigger). Bakery signup may auto-fill fields from the CNPJ (BrasilAPI), not yet decided.
- `categories` (per bakery, with sort_order) and `products` (bakery_id, category_id, name, description, price, image_url, is_available). Product photos go to Supabase Storage (`product-images` bucket). The bakery-side product management flow (CRUD UI) is not designed yet.
- `orders`: customer_id, bakery_id, `delivery_latitude`, `delivery_longitude`, `delivery_address_text` (reverse-geocoded, human-readable), status, payment_method, subtotal, delivery_fee, total, scheduled_for (null = as soon as possible), customer_notes. There is **no addresses table**; the delivery location is a snapshot taken at order time.
  - `order_status` enum: `pending -> confirmed -> preparing -> out_for_delivery -> delivered`, or `cancelled`.
  - `payment_method` enum: `pix | cash | credit_card | debit_card`.
- `order_items`: snapshot of product_name and unit_price at purchase time, so later catalog edits never rewrite history.
- `order_status_history`: filled automatically by the `log_order_status_change` trigger; powers order tracking.
- `favorite_bakeries`, `favorite_products`: composite-PK join tables per profile.
- `reviews`: one per order (`order_id` unique), 1-5 rating plus comment, only insertable for orders with status `delivered`; a trigger recomputes the bakery's `avg_rating` / `rating_count`.
- Optional, currently commented out: `subscriptions` (the "Padaria Prime" idea).

## Row Level Security (all tables have RLS enabled)

- Customers only see and create their own orders, favorites and reviews.
- Bakery owners only manage their own bakery, categories and products, and only see and update (status) the orders addressed to their bakery.
- Bakeries, categories, products and reviews are publicly readable (catalog and social proof).
- `order_items` and `order_status_history` follow the visibility of the parent order.
- The `anon` key is exposed in the front-end by design; security comes from RLS. The `service_role` key must never reach the client.

## Core Flows

1. Customer opens the app, grants location access, sees bakeries whose delivery radius covers them, picks one, browses the catalog by category and fills the cart (cart state lives client-side until checkout).
2. Checkout creates an `orders` row (status `pending`) with its `order_items`, using the device location as the delivery point.
3. The bakery sees the order, accepts or refuses it, then advances the status through preparation and delivery. Each change is recorded in `order_status_history`.
4. The customer follows the status and can review the order once it is `delivered`.

## Requirements (thesis)

Functional: RF-01 user signup/login; RF-02 bakery signup/login; RF-03 place orders; RF-04 show bakeries within delivery radius using device location; RF-05 browse catalog by category and use a cart; RF-06 track order status in real time; RF-07 bakery manages its data, categories and products; RF-08 bakery views incoming orders and updates their status.

Non-functional: RNF-01 intuitive, easy-to-use interface; RNF-02 any screen loads in up to three seconds; RNF-03 per-user data isolation via RLS; RNF-04 responsive, mobile-first, works on the main browsers and mobile devices; RNF-05 continuous availability on cloud infrastructure at no extra cost at prototype scale.

## Out of Scope / Future

Admin panel for the developer, subscription plan ("Padaria Prime"), in-app payments, loyalty program, delivery-fee zones per neighborhood.

## Commits and Pull Requests

Recent commits use concise Portuguese imperative-style subjects prefixed with `feat:` or `refactor:` (occasionally combined as `feat/refactor:`). Follow that pattern, for example `feat: adiciona recuperação de senha`. Pull requests should explain the user-visible change, list validation performed, link any related issue, and include screenshots for visual changes. Call out configuration or database changes clearly.

## Configuration and Security

Keep credentials and private keys out of source control. Configure Supabase credentials through local environment configuration, and never commit populated secret files. Review changes to authentication, route guards, and data access carefully.
